# Phase 6.5: Quibly → Zeremi rebrand & domain cutover (INSERTED 2026-05-28) - Context

**Gathered:** 2026-05-28

<domain>
## Phase Boundary

Rename the app, character, sender, and apex from **Quibly / useQuibly.com** to **Zeremi / zeremi.app** atomically enough that Phase 6 plans 06-04 (staging dry-run) and 06-05 (production go-live) launch as Zeremi and never as Quibly. Every visible string, font import, public asset, component name, env default, metadata URL, sender domain, Resend audience name, and test assertion must reflect the new brand before those Phase 6 plans run.

The phase is a **branded sweep + a single domain swap** — not a code-architecture change. No new dependencies, no new Server Actions, no new routes. The Quibs / QuibsAvatar / QuibsIcon → Zeremi / ZeremiAvatar / ZeremiIcon rename mirrors the existing component shape; the typography swap (Quicksand → Bree Serif) is a `next/font/google` swap; the asset import is a one-time copy from `marketing-app/public/brand/zeremi/`.

## Implementation Decisions

### Delivery shape
- **D-01:** **Atomic `rebrand/zeremi` feature branch; merged to main via a merge commit (no rebase, no squash).** Every Phase 6.5 plan commits to this branch as it executes (per-plan atomic commits preserved). Main stays Quibly-coherent the entire time; the merge is the brand flip. **Why:** Pre-launch traffic is effectively zero, but the symbolic cost of "useQuibly.com is up and main is half-Quibly half-Zeremi" is real, and a merge commit preserves the GSD per-plan commit-per-plan convention used in Phases 1–6. Squashing would break that 1:1 manifest-to-history mapping.
- **D-02:** **Phase 6 plans `06-04-PLAN.md` and `06-05-PLAN.md` are edited in-place on the rebrand branch** to retarget `zeremi.app` / `staging.zeremi.app`, with their UAT checklists updated to match. The ROADMAP carry-forward and the Phase 6 manifest stay accurate post-merge — no "SUPERSEDED" headers, no parallel 06.5-04 / 06.5-05 plans. Those edits land as one of the Phase 6.5 plans. **Why:** Keeps ROADMAP and STATE.md clean — Phase 6 plan IDs don't fork — and the Phase 6 plans become the natural execution surface immediately after the Phase 6.5 merge.
- **D-03:** **CI grep guard step in `.github/workflows/test.yml`** fails the build if any of `Quibly|Quibs|useQuibly\.com` reappear in source (excluding `.planning/`, `node_modules/`, generated files). Pattern mirrors `scripts/check-no-trackers.mjs` from Phase 5: a small Node script invoked as a workflow step. **Why:** SC #5 calls for the test suite to not grep for "Quibly" — the grep guard mechanically enforces the absence of the brand strings in source going forward, catching accidental copy-paste from prior phase docs or `marketing-app`. Pre-commit-only is bypassable with `--no-verify`; CI is load-bearing.

### Z-mark rendering in the hero
- **D-04:** **Mirror the existing Quibs three-component pattern exactly** for the Zeremi mark:
  - `components/zeremi/zeremi-icon.tsx` — inline SVG ported from `marketing-app/public/brand/zeremi/src/zeremi-mark.svg` (56×88 transparent Z glyph), `viewBox="0 0 56 88"`, `fill="currentColor"`, `aria-hidden`. Same file shape as the existing `components/quibs/quibs-icon.tsx`.
  - `components/zeremi/zeremi-avatar.tsx` — same `SIZE_CONFIG` (`message` / `header` / `fab`), same teal-gradient container + `inverted` prop, swapping the inner `<QuibsIcon>` for `<ZeremiIcon>`. Tailwind text utilities still drive the color.
  - `components/sections/hero-mascot.tsx` — keep filename, keep the 88×88 rounded-3xl teal-gradient (`bg-gradient-to-br from-primary to-[#14b8a6]`) wrapper, render `<ZeremiIcon width={36} height={56} />` (56:88 aspect ≈ 36:56 to roughly match the previous 48×56 mass).
  **Why:** Inline-SVG-with-currentColor is the pattern this repo already proves out — zero extra HTTP request, RSC-payload-sized, color flexibility for inverted surfaces, no LCP risk (HeroMascot is DOM-second to `<h1>` per Phase 2 D-03 and stays that way). Matches the brand-decisions note's "static Z mark" guidance while reusing the existing avatar/icon split for any future chat-surface needs.

### useQuibly.com disposition
- **D-05:** **Release `useQuibly.com` entirely** after `zeremi.app` is bound — no 301 redirect, no "we moved" static page, no SEO carry-over. The registrar registration is held as a defensive squat by the founder, but Vercel stops serving it. **Why:** Pre-launch traffic is effectively zero — there are no inbound links to preserve and no SEO juice to carry. The simplest cutover (just stop serving the old apex) has the lowest surface area for cross-domain bugs and zero ongoing maintenance.
- **D-06:** **Vercel unbinding happens inside Phase 6.5 itself** — specifically as steps in the edited `06-05-PLAN.md` production go-live checklist (after `zeremi.app` is bound and verified green). Atomic with the rebrand. **Why:** Deferring to a cleanup task leaves two domains resolving to the same deploy until cleanup ships, which risks duplicate-content noise and (more importantly) keeps the Quibly identity alive longer than the rebrand intends. Doing it inside 06-05 keeps the brand flip clean.
- **D-07:** **Delete `useQuibly.com` sender domain from Resend** after `zeremi.app` SPF + 3× DKIM + DMARC verify green and mail-tester ≥9/10 from `hello@zeremi.app`. Frees the registrar DNS records and stops any future accidental sends from `hello@useQuibly.com`. **Why:** Same reasoning as D-05/D-06 — keep one sender identity post-rebrand. The migration seed's re-intro email already plans to send from `hello@zeremi.app`; nothing needs the old sender post-cutover. The verification gate (9/10 mail-tester from the new domain) protects against deleting the old before the new is provably good.

### Resend audience handling
- **D-08:** **Rename `Quibly Waitlist` → `Zeremi Waitlist`** (production audience) AND **`Quibly Waitlist (Preview)` → `Zeremi Waitlist (Preview)`** (preview audience) in lockstep, in the Resend dashboard, during Phase 6.5. AUDIENCE_ID / AUDIENCE_ID_PREVIEW env values do NOT change (renaming preserves the IDs). Supersedes the migration-seed option (a) by doing it now while there are no real contacts. **Why:** Pre-launch the audience holds only UAT/dev signups (~0 real contacts), so zero migration risk. Renaming preserves consent_version metadata, keeps a single source of truth, and prevents the post-rebrand period where the founder sees "Quibly Waitlist" in the Resend dashboard while users see Zeremi everywhere. Lockstep on preview keeps the Phase 4 D-04 preview/prod pair semantically aligned.
- **D-09:** **`consent_version` updates automatically via the existing Phase 4 git-SHA pipeline** when `app/(legal)/privacy/page.tsx` is edited to note the rename. No code changes to `app/actions/join-waitlist.ts`. No backfill of existing contacts (none exist; backfilling would also be legally questionable). New Zeremi-era signups simply record the new SHA — exactly the audit trail the Phase 4 design intended. **Why:** The privacy-policy SHA pipeline is already correct; the rename edit naturally mints a new version. With ~0 existing contacts, the "old SHA on old contacts vs new SHA on new contacts" concern is moot.

### Claude's Discretion
- **CD-01:** **DNS provider for `zeremi.app`** — Vercel-managed nameservers (mirroring Phase 6 CD-05 for useQuibly.com) vs external (Cloudflare / registrar default). gsd-phase-researcher verifies the current registrar state during the research step and recommends; planner picks the binding sequence accordingly. Default expectation: Vercel-managed nameservers (simplest, fastest verification, matches Phase 6 pattern).
- **CD-02:** **Exact `next/font/google` Bree Serif weight axis pinning.** Bree Serif is a single-weight font (regular only); planner verifies via the next/font config that no `weight` array is needed or whether the API requires `weight: ['400']` to silence a warning. Drop the Quicksand `next/font` import entirely.
- **CD-03:** **Asset copy mechanism.** A one-shot `scripts/import-zeremi-brand.mjs` (mirrors the `scripts/rasterize-mascot.mjs` / `scripts/export-avatar.mjs` pattern) vs a documented manual `cp -r` step in the plan. Planner picks; recommendation: a script (auditable, re-runnable, leaves a commit footprint).
- **CD-04:** **Cleanup of the old Quibs assets and scripts.** Planner sweeps `public/quibs-icon.svg`, `public/quibs-icon.png`, `public/quibs-avatar*.png`, `scripts/rasterize-mascot.mjs`, `scripts/export-avatar.mjs`, `scripts/generate-wordmark.mjs` (if Quibly-specific), and the `components/quibs/` directory deletion as part of the rename plan. Anything that would survive as dead code gets dropped; the CI grep guard would fail on retained Quibs strings anyway.
- **CD-05:** **CI grep guard implementation.** Either a small `scripts/check-no-quibly.mjs` (mirrors `scripts/check-no-trackers.mjs`) invoked from `.github/workflows/test.yml` as a step, or an inline `git grep` step in the workflow. Planner picks; recommendation: standalone script, mirrors the established pattern.
- **CD-06:** **Wordmark rendering technique for the "zeremi" lowercase wordmark in the hero / footer.** Bree Serif via the `font-heading` Tailwind utility applied to a `<span>` containing the literal text `zeremi` — no pre-rasterized SVG/PNG wordmark needed. Matches marketing-app's pattern.
- **CD-07:** **Vercel domain-unbinding mechanism in 06-05.** UI-driven step (founder clicks "Remove" in the Vercel dashboard, documented in 06-UAT.md with screenshot evidence) vs `vercel` CLI. Planner picks; recommendation: UI step with screenshot (matches Phase 6 D-05 dry-run evidence convention).
- **CD-08:** **OG image regeneration.** `app/opengraph-image.tsx` currently composites the Quibs mascot PNG; rewire to `public/brand/zeremi/png/zeremi-mark-512.png` (per brand README "OG image overlay" row). Planner adjusts the `ImageResponse` JSX to the new mark + new wordmark text.
