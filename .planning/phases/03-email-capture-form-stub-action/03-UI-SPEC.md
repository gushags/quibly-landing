| Success heading ↔ body | `mt-2` (8px) | Tight grouping — body is a continuation, not a separate concern |

**Exceptions (locked, not arbitrary):**

- **Input height (≥48px touch target):** `<Input>` default is `h-8` (32px) — **insufficient for MOB-02**. Phase 3 ships the email input at `h-12` (48px) via a one-off `className="h-12"` override on the `<Input>`. This satisfies MOB-02 and is the iOS-Safari zoom floor (input must render at ≥16px font-size to suppress auto-zoom-on-focus — see Typography below).
- **Submit pill padding:** unchanged from Phase 2 — `<Button size="hero">` ships `rounded-[28px] px-9 py-3.5` (~52px tall, ≥48px ✓).
- **Honeypot positioning:** `position: absolute; left: -9999px; top: auto; height: 1px; width: 1px; overflow: hidden;` — **not** `display: none` (some bots skip those), **not** `visibility: hidden` (some screen readers expose those). Per SPAM-01 / CD-01.
- **Anchor offset (`scroll-mt-16` = 64px) preserved verbatim** from Phase 2 — Claude verified during planning that with the form rendered (vs. placeholder body) the section heading still clears the viewport edge cleanly. CD-05 closed.

## Color

The 60/30/10 split for this phase. Phase 3 introduces the **first use of `--destructive`** (validation error red) and the **first sonner toast surface** (server error). The accent (teal) reservation expands by exactly one element: the success-state checkmark icon.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (≈75%) | `--background` `oklch(1 0 0)` = `#ffffff` | Page background, form section surface, success block surface — flat white throughout (Phase 2 D-22 confirmed gradient does NOT extend below `<Hero>`). |
| Secondary (≈18%) | `--muted-foreground` `oklch(0.556 0 0)` ≈ `#888888` (microcopy, success body, sub-copy paragraph), `--foreground` `oklch(0.145 0 0)` ≈ `#111827` (input value, label, section H2, success H3), `--input` `oklch(0.922 0 0)` (input border in default state) | Body text, labels, input chrome. |
| Accent (≈5%) | `--primary` `oklch(0.6002 0.1038 184.704)` ≈ teal `#0D9488` | Submit button background (`<Button variant="default">` → `bg-primary text-primary-foreground`); success-state `<CircleCheck>` icon stroke (`text-primary`); input focus ring (`focus-visible:ring-ring/50` where `--ring` = `--primary`). |
| Destructive (≈2%) | `--destructive` `oklch(0.577 0.245 27.325)` ≈ red `#dc2626` | Inline validation error message text (`text-destructive`); input error state (`aria-invalid="true"` → existing `<Input>` `aria-invalid:border-destructive aria-invalid:ring-destructive/20` class chain — already wired in Phase 1 component). **Phase 3 is the first phase to render this surface.** |

**Accent reserved for** (explicit list — nothing else gets teal in Phase 3):
1. Submit button pill background — `<Button size="hero" variant="default">` → `bg-primary` (carry-over from Phase 2; submit consumes the same hero pill).
2. Submit button focus ring — `focus-visible:ring-ring/50` where `--ring` = `--primary` (built into the existing `<Button>` CVA).
3. Email input focus ring — `focus-visible:border-ring focus-visible:ring-ring/50` where `--ring` = `--primary` (built into Phase 1 `<Input>`).
4. Success state `<CircleCheck>` icon — `className="text-primary size-7"` (28px — see Component Inventory rationale below). **NEW in Phase 3.**
5. Sonner toast accent — sonner consumes `--popover` for toast surface and the success/info/error icons inherit current color; the **server-error toast** uses sonner's default `error` variant which renders `<OctagonXIcon>` in destructive red (already wired in `components/ui/sonner.tsx`). No additional teal use here.

**Anti-uses (do NOT apply teal to any of these):**
- Section H2 — neutral `text-foreground` (matches Phase 2 H2 styling exactly).
- Success H3 — neutral `text-foreground`. The teal lives in the icon, not the text. This keeps the visual weight on the action ("you signed up") not the language.
- Success body copy — neutral `text-muted-foreground`. Same rule.
- Email label — neutral `text-foreground`. Forms with teal labels read like marketing chrome, not utility surfaces.
- Inline error message text — `text-destructive` (red), NOT teal. Validation errors are corrective, not branded.
- Input border in default state — neutral `border-input` (existing Phase 1 chrome).
- Honeypot input — visually hidden, no color treatment needed.

**Destructive surface (NEW in Phase 3):**
- Inline validation error: `<p role="alert" className="mt-2 text-sm text-destructive">{error}</p>` rendered below the input when `state.fieldErrors.email` is set.
- Input error state: setting `aria-invalid="true"` on the `<Input>` activates the existing class chain (`aria-invalid:border-destructive aria-invalid:ring-3 aria-invalid:ring-destructive/20`) — no extra style needed. Toggle this flag from `useActionState`'s returned `state.fieldErrors.email` presence.
- The destructive surface is **silent for honeypot/time-trap rejection** (D-15) — the action returns `{ status: 'success' }` and the success block renders. No red, no "you're a bot" message.

**Sonner toast surface (NEW in Phase 3):**
- Server-error toast: triggered when `state.status === 'error'` AND `state.message` is set AND `state.fieldErrors` is undefined (D-12 routing).
- Toast renders via existing `<Toaster>` mounted in `app/layout.tsx` (D-08). Position: **bottom-right** (sonner default — CD-07). Duration: **4000ms** (sonner default — CD-07). On mobile (≤480px), sonner auto-pins to bottom-center per its built-in responsive behavior — no override needed.
- Toast variant: sonner's `error` (`toast.error("...")`) — yields the destructive red `<OctagonXIcon>` icon already wired in `components/ui/sonner.tsx`.
- Toast must respect `prefers-reduced-motion` automatically (sonner built-in). No extra guard required.
- Effect-side: the toast fires from a `useEffect` inside `<WaitlistForm>` watching `state.status === 'error' && state.message` — fires once per error response. Document this pattern in the plan.

**Color contrast ratios (must validate in plan):**
- Email input value `text-foreground` on white `bg-transparent`: ≥7.0 (AAA).
- Inline error `text-destructive` on white: ≥4.5 (AA — the destructive token at oklch ~ 0.577 against white passes ≥4.5; verify with the actual rendered hex).
- Success H3 `text-foreground` on white: ≥7.0 (AAA).
- Success body `text-muted-foreground` on white: ≥4.5 (AA).
- Submit button `text-primary-foreground` (white) on `bg-primary` (teal): ≥4.5 (AA-large at 18px+; submit text is 16px — verify).
- Sonner toast `text-popover-foreground` on `bg-popover` (`--popover` = white in light mode): ≥7.0 (AAA).

### Submit-state transitions (UX contract)

| State | Trigger | Visible UI | Underlying mechanism |
|-------|---------|------------|----------------------|

| **Pending** | User clicks submit OR presses Enter; `useActionState` sets `pending=true` until server responds | Form: input **disabled**, button **disabled** + label flips to `"Joining..."` + `<Loader2 className="animate-spin">` shows to its left of the label | Tailwind `animate-spin` (built-in, no extra CSS). | **Inline error** | `state.status === 'error'` AND `state.fieldErrors?.email` is set | Form re-renders with: input value preserved (`defaultValue` from FormData echoed by server) + `aria-invalid="true"` (red border + red focus ring via existing `<Input>` class chain) + `<p role="alert" className="text-destructive">` below the input + button re-enabled | Discriminated-union narrowing on `state` (D-10). Typed value preservation per FORM-06. |
| **Server error (toast)** | `state.status === 'error'` AND `state.message` is set AND no `state.fieldErrors` | Form returns to idle (input preserved if user typed; field error not set) + sonner toast slides in from bottom-right with `error` variant + `<OctagonXIcon>` + "Something went wrong. ### Focus management (CD-08)

- **On submit click / Enter:** native browser focus stays on the submit button until `pending=true`, at which point the button is `disabled` (focus removed by browser). Acceptable.
- **On inline validation error:** focus auto-returns to the input (the form re-renders with `aria-invalid="true"`; native `<form>` re-render keeps focus on the next focusable, which is the input since the button is briefly disabled then re-enabled). Plan: verify this behavior under React 19's `useActionState` — if focus is lost, add an explicit `inputRef.current?.focus()` inside a `useEffect` watching `fieldError`.
- **On success:** form unmounts, success block mounts with `<h3 tabIndex={-1} ref={successHeadingRef}>`. Inside `useEffect` watching `state.status === 'success'`, call `successHeadingRef.current?.focus()`. Pair with `role="status" aria-live="polite"` on the wrapping `<div>` so screen readers announce the change. Per CD-08.
- **Sonner toast:** sonner manages its own focus internally; do not manually steal focus. The toast is `role="status"` by default (announces but doesn't trap).
