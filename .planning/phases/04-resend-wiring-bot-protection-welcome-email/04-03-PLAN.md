<objective>
Ship the two server-only service singletons that wrap external SDKs:
1. `lib/resend.ts` — exports a single `Resend` SDK instance constructed from `env.RESEND_API_KEY`. Mirrors the marketing-app pattern (`marketing-app/lib/email/client.ts`) but routes through `@/lib/env` per Phase 1 D-11. Imported by Plans 05 (action body), 06 (webhook + unsubscribe routes).
2. `lib/rate-limit.ts` — exports two `Ratelimit` instances forming the sliding-window ladder (5/min/IP + 50/day/IP per SPAM-03). Uses `Redis.fromEnv()` which automatically reads `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN`.

Purpose: Both libs are pure SDK-wrapping singletons with no business logic — they isolate the SDK construction so the action body (Plan 05) can `import { resend } from '@/lib/resend'` and `import { rateLimitPerMinute, rateLimitPerDay } from '@/lib/rate-limit'` without touching SDK construction details. `import 'server-only'` on both files crashes the build if a client component transitively imports either, which prevents `RESEND_API_KEY` from ever bundling to the client.

Output: Two new server-only `lib/*.ts` files. No tests in this plan — these are pure SDK-construction singletons with nothing to assert beyond "module loads without throwing"; the Plan 05/06 unit tests will mock both via `vi.mock(...)` and provide the real assertions on usage.
</objective>

    Write `lib/rate-limit.ts` exactly as below. Two named exports — `rateLimitPerMinute` and `rateLimitPerDay` — backed by a single `Redis.fromEnv()` instance. SPAM-03 requires both: 5/min/IP for burst defense, 50/day/IP for sustained-flood defense.

    ```typescript
    import 'server-only'
    import { Ratelimit } from '@upstash/ratelimit'
    import { Redis } from '@upstash/redis'

    /**
     * Phase 4 sliding-window rate limit ladder (SPAM-03).
     *
     * Two limiters run in parallel against every signup IP:
     *   - 5 requests / 60s   — burst defense (defeats scripted high-frequency abuse)
     *   - 50 requests / 1d   — sustained-flood defense (defeats slow-drip campaigns)
     *
     * A signup is silently rejected (D-03) only if BOTH `.success` flags are evaluated
     * by the action body; if either limiter fails, the action returns success-shape
     * with no welcome email and no `track('waitlist_signup')` event.
     *
     * Pitfall 5: rate limit is checked AFTER honeypot/time-trap (Phase 3) and AFTER
     * disposable-domain (CD-11) — bots that trip earlier defenses do NOT increment
     * the IP's rate-limit bucket. Order is enforced in Plan 05's action body.
     *
     * `Redis.fromEnv()` reads UPSTASH_REDIS_REST_URL + UPSTASH_REDIS_REST_TOKEN
     * from process.env inside the @upstash/redis package. Phase 1 D-08 boot-validation
     * via lib/env.ts guarantees both vars are present before any module loads.
     *
     * `analytics` is omitted (defaults to false) per RESEARCH Pattern 3 — keeps
     * the implementation simple; no `context.waitUntil(pending)` plumbing required.
     */

    const redis = Redis.fromEnv()

    export const rateLimitPerMinute = new Ratelimit({
      redis,
      limiter: Ratelimit.slidingWindow(5, '60 s'),
      prefix: '@quibly/ratelimit/min',
    })

    export const rateLimitPerDay = new Ratelimit({
      redis,
      limiter: Ratelimit.slidingWindow(50, '1 d'),
      prefix: '@quibly/ratelimit/day',
    })
    ```

    Notes for the executor:
    - Do NOT add `import { env } from '@/lib/env'` here — `Redis.fromEnv()` reads its own env vars; pulling them through `lib/env.ts` would require destructuring then re-passing to `new Redis({...})`, which adds noise without value. The Phase 1 boot validation already enforces presence.
    - Do NOT pass `analytics: true` — RESEARCH Pattern 3 explicitly recommends `false` (default) for Phase 4 to avoid `context.waitUntil(pending)` plumbing.
    - The two `prefix` values MUST be different (`@quibly/ratelimit/min` vs `@quibly/ratelimit/day`) so the two limiters don't share Redis keyspace and trip each other.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client component → lib/resend.ts | `import 'server-only'` blocks any client import; build fails if violated |
| lib/resend.ts → Resend API | Restricted "Sending access" key scope (STORE-02) — cannot read other audiences or full account state |
| lib/rate-limit.ts → Upstash Redis | Authenticated by REST token (UPSTASH_REDIS_REST_TOKEN); operates only on `@quibly/*` keyspace prefixes |
| public IP → rate-limit bucket | IP-keyed buckets — shared NAT (corporate, conference WiFi) might trip the limit; D-03 silent-success contains the impact |
